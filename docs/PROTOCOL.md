# Wack-OS UART Protocol v1

Текстовый, строчный протокол поверх UART. Один кадр — одна строка,
завершённая `\n`. Человекочитаемый специально: должно быть видно
в обычном serial-терминале без декодера.

Протокол не знает, кто на другом конце провода — ESP32, STM32, RP2040.
Это единственный контракт между master и slave.

## Общая грамматика кадра

```
<ROLE> <ADDR> <FIELD> <SEQ> <PAYLOAD> <CSUM>\n
```

| Часть   | Формат                          | Описание                                              |
|---------|----------------------------------|--------------------------------------------------------|
| ROLE    | `REQ` / `RES` / `EVT`           | тип кадра (запрос / ответ / асинхронное событие)       |
| ADDR    | 2 цифры, `00`-`99`               | адрес slave-устройства. `00` = broadcast (зарезервировано на будущее, для шины из нескольких slave) |
| FIELD   | строка без пробелов             | в `REQ` — имя команды; в `RES` — `OK` или `ERR`; в `EVT` — имя события |
| SEQ     | 4 hex-цифры, `0000`-`FFFF`       | номер кадра. `RES` обязан повторить `SEQ` своего `REQ`. `EVT` использует отдельный счётчик slave |
| PAYLOAD | `-` либо произвольная строка      | аргументы/данные. Может содержать пробелы: CSUM отделяется **последним** пробелом строки, а полей перед payload ровно четыре, поэтому остаток строки — это весь payload. `-` = нет данных |
| CSUM    | 2 hex-цифры                     | XOR8 всех байт кадра от `ROLE` до `PAYLOAD` включительно (разделители-пробелы тоже участвуют), выводится заглавными hex-цифрами |

Разделитель полей — ровно один пробел. Строка заканчивается `\n`
(без `\r`).

Единственное ограничение на содержимое payload — в нём не может быть
`\n` (это конец кадра). Пробелы допустимы: парсер сначала отрезает
CSUM по последнему пробелу, а всё, что осталось после четырёх первых
полей, считает payload целиком. Так `RES 01 OK 000C Hello from slave! 2A`
разбирается в payload `Hello from slave!`, а не `Hello`.

### Пример

```
REQ 01 SYS_PING 0007 - 4F
RES 01 OK 0007 PONG 3A
```

## Адресация

Сейчас в устройстве всегда ровно один активный slave — master
общается с ним по фиксированному адресу `01`. Адрес `00` зарезервирован
под broadcast/автообнаружение — не используется в v1, но поле уже есть
в грамматике, чтобы потом перейти на шину (RS485 и т.п.) с несколькими
slave без ломки формата.

Кадр с чужим `ADDR` slave обязан **молча игнорировать** — не отвечать
ни `RES OK`, ни `RES ERR`. Для отправителя это выглядит как "такого
устройства нет", и именно это делает возможной шину: иначе на один
запрос ответят все разом. Свой адрес сторона задаёт вызовом
`wackos_proto_set_address()`; по умолчанию — `01`.

## Три типа кадров

- **REQ** (master → slave) — запрос. Ждёт `RES` с тем же `SEQ`.
- **RES** (slave → master) — ответ на конкретный `REQ`. `FIELD` = `OK`
  или `ERR`. При `ERR` первое значение `PAYLOAD` — код ошибки (см. ниже).
- **EVT** (slave → master) — асинхронное событие без предшествующего
  запроса (прогресс долгой операции, данные с датчика и т.п.). Не
  требует ответа. Нужно для команд, которые не укладываются в
  синхронный запрос-ответ (например, будущий `RADIO_SCAN`): `REQ`
  сразу возвращает `RES OK ACCEPTED`, а результаты приходят потоком
  `EVT`.

## Таблица команд (v1)

Пространства имён команд зарезервированы префиксом модуля — так новые
модули не пересекаются друг с другом.

| Команда        | Namespace | Payload запроса         | Payload ответа (OK)         | Статус         |
|----------------|-----------|--------------------------|------------------------------|----------------|
| `SYS_PING`     | SYS       | `-`                       | `PONG`                        | реализовано    |
| `SYS_VERSION`  | SYS       | `-`                       | `<версия_прото>,<версия_прошивки>` | реализовано |
| `SYS_CAPS`     | SYS       | `-`                       | список поддерживаемых команд через `;`, напр. `SYS_PING;SYS_VERSION;UI_MENU_GET` | реализовано |
| `SYS_RESET`    | SYS       | `-`                       | `OK` затем slave перезагружается | реализовано |
| `UI_MENU_GET`  | UI        | `-`                       | `<id1>:<title1>;<id2>:<title2>;...` — плоский список пунктов меню, которые умеет slave | реализовано |
| `UI_MENU_SELECT` | UI      | `<id>`                    | произвольная строка-результат (пробелы можно), которую master просто показывает | реализовано |
| `ENC_GET`      | ENC       | `-`                       | `<поворотов_со_знаком>,<коротких_нажатий>,<длинных>` — накопленное с прошлого запроса, счётчики обнуляются | реализовано (временно, см. ниже) |
| `RADIO_*`      | RADIO     | —                         | —                             | зарезервировано, заглушка → `E_NOT_SUPPORTED` |
| `HID_*`        | HID       | —                         | —                             | зарезервировано, заглушка → `E_NOT_SUPPORTED` |
| `SENSOR_*`     | SENSOR    | —                         | —                             | зарезервировано, заглушка → `E_NOT_SUPPORTED` |

Любая нераспознанная команда (в том числе `RADIO_*`/`HID_*`/`SENSOR_*`
до появления реализации) отвечает `RES <addr> ERR <seq> E_UNKNOWN_CMD`
или `E_NOT_SUPPORTED`, если namespace распознан, а конкретная команда —
ещё нет. Это разграничение полезно для UI: "модуля вообще нет" и
"модуль есть, но эта функция пока не реализована" — разные состояния.

## События (EVT)

| Событие | Payload                          | Кто шлёт | Когда |
|---------|----------------------------------|----------|-------|
| `ENC`   | `CW` / `CCW` / `BTN` / `BTN_LONG` | slave    | повернули или нажали энкодер |

Пример:

```
EVT 01 ENC 0003 CW 6B
```

### Почему энкодер на slave — это временно

По архитектуре ручка принадлежит master: он рисует интерфейс и слушает
ввод. Но платы master пока нет, а энкодер есть, поэтому он подключён к
slave, и его события уезжают на master кадрами `EVT` — ровно тот
случай, ради которого `EVT` и заведён.

Когда master приедет, модуль `ENC_*` со slave убирается, master читает
свою ручку сам, и интерфейс разницы не замечает: события те же самые,
потому что декодер (щелчки, длинное нажатие) — общий код
`components/wackos_encoder`.

Пока master занят собственным запросом, у него есть место лишь под одно
отложенное `EVT`, так что при очень быстром кручении во время обмена
события могут потеряться. На этот случай есть опросный `ENC_GET` со
счётчиками — он ничего не теряет.

## Коды ошибок

| Код               | Значение                                              |
|-------------------|---------------------------------------------------------|
| `E_UNKNOWN_CMD`   | команда не распознана вообще                            |
| `E_BAD_ARGS`      | payload есть, но не соответствует ожидаемому формату    |
| `E_BUSY`          | slave занят предыдущей операцией                         |
| `E_NOT_SUPPORTED` | namespace распознан, конкретная команда — нет (заглушка) |
| `E_INTERNAL`      | внутренняя ошибка slave (модуль упал и т.п.)             |
| `E_CRC`           | не сошлась контрольная сумма входящего кадра             |

## Тайм-ауты и ретраи

- Дефолтный тайм-аут ожидания `RES` на master — **150 мс**.
- При тайм-ауте master повторяет `REQ` с тем же `SEQ` — до **2 ретраев**
  (итого 3 попытки, максимум ~450 мс).
- После исчерпания ретраев master считает slave отключённым/зависшим и
  показывает это в UI явным состоянием ("SLAVE OFFLINE"), не падает.
- Для долгих операций (когда `REQ` отвечает `OK ACCEPTED` и дальше идут
  `EVT`) действует отдельный сторожевой тайм-аут отсутствия `EVT`
  (по умолчанию 5 с) — если долго тишина, UI помечает операцию
  прерванной.
- `SEQ` инкрементируется master на каждый новый `REQ` (по модулю
  0x10000) — используется, чтобы отбросить запоздавший `RES` от старого
  ретрая, если он всё же пришёл после того, как ретрай уже "победил".

## Версионирование протокола и расширяемость

- Добавление новой команды = добавление новой строки в таблицу выше.
  Старые команды не меняются — обратная совместимость по умолчанию.
- Неизвестные команды не роняют slave — отвечают `E_UNKNOWN_CMD`, так
  что master со старым протоколом и slave с новым (или наоборот) не
  ломают друг друга, а просто не видят новых возможностей.
- Если когда-то понадобится бинарный/более компактный вариант —
  меняется только транспортный/сериализационный слой, сама модель
  "REQ/RES/EVT, ADDR, SEQ, коды ошибок" остаётся.
